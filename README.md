# 顺手（shunshu）

监控小说**目录页**有没有更新的小工具。Windows 托盘常驻，没有窗口界面：添加、删除、改间隔、看状态全在托盘右键菜单里，更新提醒用右下角卡片。

只做一件事：抓目录页 → 认出章节容器 → 比对新旧章节 → 有更新就弹卡片。正文一律不下载，点章节交给默认浏览器打开。

## 快速开始

双击项目根的 **`启动.bat`**：后台起托盘，不留控制台窗口；首次运行会自动 `uv sync` 装依赖。排错用 `启动.bat debug`（带控制台启动，异常直接看得见）。

重复双击不会多出第二个图标——第二个实例会弹一张「顺手已经在运行」的卡片然后自己退出。

手动启动（与双击等价，会占着控制台）：

```bat
uv sync
uv run shunshu
```

开机自启：托盘菜单勾「开机自启」（写 HKCU 的 `Software\Microsoft\Windows\CurrentVersion\Run`，源码态用 `pythonw.exe` 起、打包态直接用 `shunshu.exe`，都不占控制台）。

添加小说：在浏览器里复制目录页网址 → 托盘「添加小说（从剪贴板）」。抓完直接弹一张卡片，列出**最新的 5 章**让你确认认对了书（顺手点一章就能开始看，并记为已读）；书名从页面标题里取，这一轮只记基线、不算更新。

## 托盘菜单

- **小说列表** → 每本一个子菜单：`打开最新章节`（跳浏览器并记为已读，跨来源取最新的那一章）、`添加来源到本书（从剪贴板）`、`暂停/恢复本书`、`删除本书`（要先点一次「确认删除本书？」）；识别失败时还会给出候选容器文件路径。
- **来源子菜单**：书下面逐个列出该书的**来源**，行上写着站点、状态、（手写过代理时的）代理地址，主源那行标「（主源）」。点开某一源：第一行是它的目录页网址，然后是最后一章与章节数、**这一源实际走的代理**（`直连（不走系统代理）` / `http://127.0.0.1:7890（手写覆盖）`），再往下是 `设为主源`（已经是主源时灰着）、`暂停此源 / 恢复此源`、`删除此源`（同样点两次确认）。删掉最后一个来源等于把整本移出书架。
- **添加小说（从剪贴板）**：从剪贴板文本里提 http(s) 网址；同一网址重复添加会提示。
- **重新加载配置**：手改过 `data/novels.json` / `data/config.json` 后点这里生效，不用重启。
- **扫描间隔**：5 / 10 / 30 / 60 分钟，四选一，默认 30 分钟（固定间隔，不做抖动）。
- **开机自启**：勾选状态即当前注册表项是否存在。
- **打开数据目录** / **退出**。

## 更新卡片

一个弹窗只说一本书。这本书挂了多个来源时，**同一次检查里几个来源各自更的章会合成一张卡**，卡片固定列**最近的 5 章**（不管这次更新了几章），按章节顺序从新到旧排：

- **绿色** = 没读过；**灰色** = 已经点开过。用来确认自己有没有漏看。
- 每行右边标出**这一章是最先由哪个来源报上来的**（谁先更就归谁），标题写成「《书名》更新 N 章（来自 A、B）」；更的章只有镜像站报了、主源没报，标题会再加一句「主源未更新」。
- **同一章只提醒一次**：镜像站报过「第61章」之后主源才更出同一章，不会再弹第二遍（繁简站标题不同也算同一章）。
- 点任意一章：交给默认浏览器打开，该章记为已读，卡片自己收起。
- 点「关闭」：只收起卡片。12 秒没人理它也会自动消失。
- 多张卡按**槽位**排布：每张卡占一个槽位约 12.5 秒，短时间内连来两批更新也不会叠在同一位置；一列排满屏幕高度就自动向左换一列。

刚添加一本时弹的是同一种卡片，标题换成「已添加《书名》」，列最新的 5 章（此时都还没读过，全绿）。往一本已有的书里**追加来源不会再多弹一张卡**——那张卡是该书第一次进书架时弹的。

「已读」的判定就是**你通过本工具点开过这一章**（卡片上点的、或托盘里点「打开最新章节」）。工具不下载正文，所以没法知道你在浏览器里读过什么——直接在网站上看的章节不会变灰。

## data/ 目录

运行时生成在项目根（打包后在 exe 同级）：

| 文件 | 内容 |
| --- | --- |
| `novels.json` | 书架。每本小说一段：`title`、`primary_id`（主源）、`read_keys`（点开过的章节，**跨来源共用**）、`alerted_keys`（已经弹过卡的章节，跨来源共用，重启后靠它不重复弹）、`chapter_index`（最近若干章的索引：章节号、标题、URL、最先报它的来源，卡片就按这个排）、`sources`（这本书的所有来源）。每个来源有自己的 `toc_url`、`site`、`selector`、`proxy`、`keep_keys`/`drop_keys`、`notified_keys`（本站已提醒过的章节）与状态。可手改，改完走「重新加载配置」 |
| `config.json` | 抓取与广告名单，缺省即内置默认值；`site_proxies` 是添加书源时自动探测的站点代理记忆（主机名 → 代理 URL，空串为直连），可手改/删键 |
| `history/<novel_id>/<source_id>.jsonl` | 按来源分开存的检查记录：`baseline` / `update` / `toc_reset` |
| `candidates/<source_id>.txt` | 识别失败时导出的候选容器与被过滤链接 |
| `filtered.log` | 每轮被当成广告丢掉的链接（原因 + 文本 + URL） |
| `alerts.log` | 每次弹窗的内容与跳转地址 |
| `read.jsonl` | 卡片进程写的已读记录（`novel` + 跨源章节身份 `key`），主程序下一轮吸收进 `novels.json` 后清空 |
| `shunshu.log` | 运行日志，一轮一行 |

两个保命小机制：

- **手滑改坏 JSON 不会起不来**：`config.json` / `novels.json` 解析失败时，原文件改名成带时间戳的 `*.YYYYmmddHHMMSS.bak` 留在 `data/` 里留现场，程序按默认配置 / 空书架启动，启动卡或「重新加载配置」回执会写明备份文件名；书架里只有单条写坏则跳过那一条、其余照载——**下一级**写坏也一样只挡那一条（`sources` 里不是对象的那项、缺 `id` 或没有 `toc_url` 的来源、索引里缺 `k` 的行都单独跳过，字段类型不对按空值处理，来源缺 id 会按 `toc_url` 补算，整本/整源 id 重复的挡掉后面那份并写明原因）。
- **日志按 2MB 自动轮转**：追加型日志（`shunshu.log` / `filtered.log` / `alerts.log` / `history/*.jsonl`）超过 2MB 时按行边界只留尾部 75%，长跑几年也不会把磁盘吃掉。

`version` 为 2。**一本挂多个来源**日常走托盘「添加来源到本书（从剪贴板）」，直接手改也行：在同一本小说的 `sources` 数组里追加一项，`id` 用目录页 URL 的 sha1 前 12 位。不同站点、繁简站混着放都行——同一章在各来源上会归一到同一个跨源身份，已读与提醒都按这个身份合并。

## 代理怎么配

**添加书源时会自动确认一次**：托盘「添加小说」或「添加来源到本书」后，程序先**直连**目录页，通了就记下这个站直连；只有直连**连不上**（连接被拒、超时、DNS 失败，一个 HTTP 答复都没拿到）才依次试本机代理（先读 Windows LAN 设置里的系统代理，再兜底试 Clash/v2rayN 等常见本机端口 7890/7891/10809/10808 等；同一端口的 http/https 写法只探一次）。站点只要给了 HTTP 答复（哪怕 4xx/5xx/空页），就说明这条网络路径是通的，不会因为一次临时 503 就误判成「需要代理」。试出某个代理能通，就把代理地址写到该来源上，**后续每一轮都走它**，探测时抓回的首页 HTML 直接复用给首轮建档，目录页只敲一次门；直连和代理都不通则书照加、不记忆，弹卡片指引你手写代理。探测只在添加时做一次（超时 6 秒、不重试），日常轮询绝不临时探测——唯一的例外：**当初由探测自动写上去的**代理连续失败到退避阈值（默认 5 次）会自动重探一次，你把代理客户端从 7890 换成 10809 后无需手改配置即可自愈。你在 `novels.json` 手写的 `proxy` 永远不会被自动覆盖，也**不参与自动重探**（一个包都不会替它试）：它失败就照常累计次数、照常进退避，改不改由你决定。

结论存在两个地方：

- `data/config.json` 的 `site_proxies`：**站点级记忆**，形如 `{"m.proxy-book.example": "http://127.0.0.1:7890", "reading.example": ""}`，值为空串表示该站直连可达（`www.` 前缀归一）。同站点再添来源直接套用，不再探测。删掉某个键，下次添加该站时会重新探测。
- `data/novels.json` 里该来源的 `proxy`：**这个来源实际使用的值**，添加时由探测结果自动填入。

**运行时只认来源自己的 `proxy`**：抓取器不读环境变量（`HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`）也不读 Windows 的 LAN 系统代理（`Session.trust_env=False`）——系统代理只在添加探测那一下用来找候选。想手动调整直接改文件：

```json
{
  "id": "3f2a1c9d8b70",
  "toc_url": "https://繁体站.example/12_3456/",
  "proxy": "http://127.0.0.1:7890"
}
```

清空 `proxy` 改成直连、或换成别的代理都行（只影响这一个来源，不会动站点记忆）；只接受 `http://`、`https://`、`socks5://` 三种前缀，必须带协议名；`socks5://用户:密码@127.0.0.1:7890` 这种带账号的写法也有效，但显示与日志里只会留 `socks5://127.0.0.1:7890`。改完托盘点「重新加载配置」。

**想知道某一源实际走了什么**：托盘 → 该书 → 该来源，子菜单里那行「代理 …」就是结论——没写就是 `直连（不走系统代理）`，写了显示脱敏后的代理地址加「（手写覆盖）」。菜单只负责显示，设置入口仍是 `novels.json` / `config.json`。

抓不动时状态会分得很清：

- **代理不可用**＝代理本身不通（代理软件没开、端口写错、忘了带协议前缀）。这类错误重试也不会好，直接记一次失败并进入退避；**当初探测写上去的**代理连续失败到阈值还会自动重探一次（手写覆盖不参与重探，失败照常累计、退避照常生效）；原因原话（例如 `[WinError 10061] 由于目标计算机积极拒绝`）就写在这本书该来源的那一行里，托盘菜单直接看得到。
- **网络错误**＝代理/网络是通的，但站点没给可用内容：连接被拒/超时/DNS（连不上）、SSL 证书失败、断链、HTTP 4xx/5xx、空页或非 HTML。其中 **4xx 是站点的明确答复，不重试立刻失败**；5xx 多为临时故障，会退避重试；只有「连不上」这一类才会在添加探测时触发改走代理。
- **解析失败**＝页面抓到了但认不出章节容器，去看 `data/candidates/<source_id>.txt`。
- **检查异常**＝这一个来源撞上了没预料到的错（不是站点给的答复）。只算这一个来源的失败、照常进退避，同一轮别的来源与这本书的提醒都不受影响；异常类型与原因写在 `data/shunshu.log` 里，托盘那一行也直接看得到。

## 识别失败怎么修

盗版站改版后可能认不出章节容器，托盘里该书会显示解析失败原因。步骤：

1. 打开 `data/candidates/<source_id>.txt`，里面按得分列了候选容器的 CSS、链接数、章节样式数、广告数和样例。
2. 挑最像的那个，把它的 CSS 填进 `data/novels.json` 里该书 `sources` 中这一项的 `"selector"`（填**容器**，不是单条链接），例如 `"selector": "div.listmain dl"`。手写了 selector 也照样跟末页；第二页结构不同、这个 selector 认不出时，就退回只用首页的章节，不会把整次检查判失败。
3. 托盘「重新加载配置」。急着看结果就把该书删掉重新添加一次（添加会当场抓取并弹卡），或等下一个扫描间隔。
4. 误杀章节：把该章 URL（或标题）填进该来源的 `keep_keys`；漏进来的广告：填进 `drop_keys`。两者都支持归一化 URL、原始 URL、标题三种写法。

内置的判定不是「必须有第X章」：章节号支持中文数字与 `1001.` 形式编号，倒序目录、分页目录都能处理——有「末页」跟末页，只有「下一页」的两页站也跟着翻一页，只认同目录下的翻页链接，`/module.php?go=next` 这类假翻页不敲。一次冒出过多新章节（超过 30 章，或新标识占当前目录比例超过 `toc_reset_new_ratio`，默认 0.6，可在 config.json 调）、或已知章节大面积消失（重合率低于 `toc_reset_overlap_ratio`，默认 0.35），会判为「目录被重置/整站改版」并记录但**不提醒**，避免把整本书当新章节刷屏；刚开始多跟到一页时不算重置，那批新章是真新章。

## 打包成 exe

不需要手动打包也不需要手动打 tag：CI（`.github/workflows/build.yml`）在每次 push 到 `main` 时都会跑测试、用 Nuitka 编出 standalone 目录，并按 `pyproject.toml` 里的版本号自动发布到 **Releases**（tag 不存在时由 CI 建）。所以发版动作就是「改版本号 + push」。手动打 `v*` tag 也能触发，用于补发某个版本。

每次发两个包，按需取用：

| 资产 | 内容 | 适合 |
| --- | --- | --- |
| `shunshu-<版本>-windows-amd64.zip` | folder 模式：`shunshu.exe` + 依赖目录，解压即用 | 启动最快，首次运行不解包 |
| `shunshu-<版本>-windows-amd64-onefile.exe` | 单个 exe | 拷一个文件就走；首次运行解包到 `%LOCALAPPDATA%` 下按版本固定的缓存目录 |

单文件模式用了 `--onefile-cache-mode=cached`：解包目录固定，**主进程和弹卡片用的子进程共用同一份**，否则每弹一张卡就要重解一次几十 MB。这也是它必须带 `--company-name/--product-name/--product-version` 的原因（默认路径模板要用这几个值）。代价是 CI 要多编一次，构建时间大约翻倍。

同一个 `shunshu.exe` 兼任两件事——直接运行是起托盘，`shunshu.exe popup --payload <json>` 是主程序弹卡片时调的子命令。「当前是不是打包态、再次拉起自己该用哪个 exe」统一由 `packaging.py` 回答（PyInstaller 认 `sys.frozen`；Nuitka 判「argv[0] 是真实文件而 sys.executable 指向的解释器不存在」，因为它会把 `sys.executable` 伪造成一个不存在的 `python.exe`），开机自启命令、`data/` 目录定位、卡片子进程拉起都用这同一结论——Nuitka onefile 升级后解包临时目录会变版本号，`data/` 因此锚定在真实 exe 同级而不是 `__file__` 旁边，书架和代理记忆不会随升级「丢失」。编译参数以 workflow 里那两条为准，本地跑同样的命令即可（需要先 `uv sync --group dev`）。

## 设计与取舍

- **入口只有两个**：托盘右键菜单，和直接改 `data/*.json`。不提供命令行——`shunshu` 这个命令只做一件事（起托盘），`python -m shunshu popup` 是主程序弹卡片时自己调用的内部子命令。
- **不用 Windows 原生 toast**：非打包进程在这台机器上注册不了 AUMID，WinRT 的 `Show()` 不报错但通知会被静默丢掉。所以卡片是自己用 Tk 画的、由短命子进程弹出的无边框窗口（`python -m shunshu popup --payload <json>`）。
- **只放行 http(s)**：任何要交给 shell / 浏览器的 URL 都先过 `assert_http_url`，`javascript:`、`data:`、本地路径一律拒绝；卡片里显示的跳转地址也会先过滤再写日志。
- **跳板链接不在服务端跟随**：`/b.php?url=...` 这类章节链接原样保留，交给浏览器完成跳转，少一次请求就少一次风控暴露。
- **同站串行 + 间隔**：并发只用于不同站点（默认 6），同域名单线程并留 2 秒间隔；响应体大小、超时、重试退避都有上限。并发线程池**常驻复用**（工作线程内的 Session 与 keep-alive 连接跨轮存活，改并发配置才重建），不再每轮新建销毁。检查单本书时也照「锁内取快照、锁外抓取」走，抓取期间托盘菜单不卡死。
- **内置名单永远生效**：广告/后缀内置名单与 `config.json` 里的用户名单合并去重后使用，老用户文件里固化的旧名单也能收到版本自带的新默认项，用户自己加的条目原样保留。
- **编码**：盗版站大量 gb18030，按 header → meta → utf-8 → gb18030 的顺序定编码，声明 gb2312/gbk 的一律按 gb18030 解。
- **最新章节按目录自己的排列定**：把抓到的章节按目录出现顺序排成旧→新，再用相邻编号的升降投票判断这本书是正序排还是倒序排（倒序站取开头，正序站取末尾）。**站点自己把编号写乱时不猜编号**——有的站正文排到 1564 章，末尾又另挂一块 184~190 章，那块才是最新，按编号取就永远取错。跨来源比较仍按章节号（同源的乱序只在源内按排列解决）。
- **TLS 用 Windows 系统证书库**：盗版站常常只发叶子证书、少发中间证书，浏览器会自己补链，certifi 不会，于是浏览器能开的站在工具里报 `CERTIFICATE_VERIFY_FAILED`。抓取器启动时把默认证书库换成系统库（`truststore`），代理软件自签的 CA 装进系统库也就跟着信；换不了就退回 certifi，不会更差。**验证没有关掉**，只是换成本机信得过的那套根。
- **章节身份**：来源内去重用 `normalize_chapter_url` 归一化后的 URL（协议统一 https、去 www、去 index.html 与尾斜杠、去 fragment 与跟踪参数、去默认端口，业务参数保留）。改名、换协议都不会重复提醒。
- **跨来源认同一章**：用「章节号 + 正题」的 `match_key`——正题先转简体、剥掉「第X章/1001.」序号前缀与「（求月票）」这类括号标注，只留汉字数字和小写字母再比对。繁简两个来源的「第120章 風雪夜歸人」和「第120章 风雪夜归人」因此认得出是同一章，已读状态共通：在一边点开过，另一边那张卡片里也是灰的。**显示也统一成简体**——卡片、托盘菜单里都是简体，但 `data/history/` 与 `novels.json` 存的是源站原文，跳过去的网页仍是繁体原样。
- **状态分两层**：`notified_keys` 按来源记（各站 URL 不同），`read_keys`、`alerted_keys`、`chapter_index` 与书名按小说记；书名以最先抓到的来源为准，之后不再改写。
- **提醒按小说记，抓取按来源记**：一轮里各来源的新章先按来源自己的 `notified_keys` 判新，再用 `match_key` 在小说级去重后合成一张卡。卡片只列最近几章，索引默认留 50 章。记账与弹卡是分开的两步：先按小说级去重把这一轮的章节记进 `alerted_keys`，再决定弹不弹，所以卡片没弹成（子进程起不来、被系统丢掉）也不会漏记，同一章不会再来一遍。
- **`notified_keys` 先记全目录，再记历史**：`notified_keys_keep`（默认 500）只裁**已经不在目录里**的历史 key，目录还列着的章节一个都不能忘——一本 1600 章的书要是被裁掉一半，下一轮就会把那 800 章全当成新更新，永远卡在「疑似重编号」里出不来。
- **新来源的基线不算更新**：中途挂上来的慢镜像首轮只建基线，那批章节直接并进 `alerted_keys`，所以主源几周前就报过的章不会被它当成新章刷屏。
- **默认直连，添加时自动确认，`proxy` 按来源单独开**：`Session.trust_env=False`，环境变量和 Windows 系统代理在日常抓取时一概不读，代理软件开着也不会把国内站绕一圈。添加书源时只探测这一次——先直连，不通再从 Windows LAN 设置和常见本机端口找代理试，结论写进 `config.json` 的 `site_proxies`（站点级记忆）和来源的 `proxy`；之后每轮只按配置走，不临时探测。只有要代理的那一个来源走代理，另一个来源照常——繁简站常常一边要代理一边不要。代理不通单独记 `代理不可用`，不重试、不跟「解析失败」混在一个状态里；交给日志与托盘的代理地址一律去掉账号密码。来源子菜单里那一行「代理 …」显示的是**实际生效**的结果（手写覆盖 / 直连），设置入口为 `novels.json` 与 `config.json`。
- **失败退避**：某个来源连续失败 5 次后跳过若干轮，成功即清零；一个来源挂了不影响同一本书的其它来源。
